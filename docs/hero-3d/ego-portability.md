# EGO-Swarm 与主页交互场景：移植范围和资源预算

2026-09-09。本文是源码核查与工程估算，未编译 WASM、未运行原生规划器基准，也没有测得访客设备的 GPU 显存。

建议保留主页的轻量巡航，把真正的 EGO 能力逐步放进可选择的研究演示。Three.js 可以完整呈现 EGO 生成的轨迹，但渲染器不会自动获得避障、动力学约束或分布式规划能力。原生核心可以迁移到浏览器中的独立计算模块；不适合直接塞入 `scene.js` 的逐帧循环。

## 目前具备什么，缺少什么

当前网站提供可视化编队、航点平移、手动控制和巡航。即便路径变成平滑的 8 字，也不能称作 EGO-Swarm：尚无占据地图、碰撞约束优化、异步邻机轨迹交换、可行性检查和失败后的安全轨迹。这次 UI/动画升级没有移植 EGO 算法。

官方系统的定位是未知障碍环境中的分散、异步多机导航；“固定编队形状”并不是原生避障保证。需要允许各机暂时偏离编队绕障，随后再恢复队形。[EGO-Swarm 论文](https://arxiv.org/abs/2011.04183)

本次检查的本地基线：`ego-planner-swarm-basic`，Git 提交 `92fe9f7227b2da819133eb8e0e8c7fc000f6ae20`，origin 为 [FAST Lab 官方仓库](https://github.com/ZJU-FAST-Lab/ego-planner-swarm)。下面的实现判断来自该提交，不表示最新版所有分支完全相同。

| 本地文件（相对基线根目录） | 实际内容及移植影响 |
|---|---|
| `src/planner/bspline_opt/src/uniform_bspline.cpp` | B-spline 求值和导数；适合作为最先独立出来的数学层。 |
| `src/planner/traj_utils/msg/Bspline.msg` | drone ID、order、traj ID、start time、knots、位置控制点及 yaw 字段；可以映射成有版本的 JSON/二进制协议。 |
| `src/planner/bspline_opt/src/bspline_optimizer.cpp` | 平滑、距离反弹、速度/加速度可行性、邻机和终点成本；包含 L-BFGS 迭代和重试。不能用普通样条插值替代后仍声称原生 EGO。 |
| `src/planner/plan_manage/src/ego_replan_fsm.cpp` | 0.01 s FSM 定时器、0.05 s 安全检查定时器、邻机轨迹接收与重规划。定时器频率不等于每次都进行一次优化。 |
| `src/planner/plan_env/src/grid_map.cpp` | 占据、膨胀、射线计数缓存和深度/点云 ROS 输入；需拆成无 ROS 的地图接口。 |
| `src/planner/plan_manage/src/planner_manager.cpp:40` | 每个 planner 初始化 `100×100×100` 的 A*节点池。 |
| `src/planner/path_searching/src/dyn_a_star.cpp` | 对上述百万个节点逐个 `new`；这是直接移植时很容易忽略的内存和启动成本。 |

CMake 当前使用 ROS/catkin、Eigen、PCL；环境层还有 OpenCV/cv_bridge/message_filters。浏览器版应保留所需数学和优化器，替换参数、时钟、日志、地图访问、消息收发，不把整套 ROS、RViz 和传感器模拟器都打包进去。官方仓库也提供 ROS2 分支，但换 ROS 版本不等于已经支持 WebAssembly。[官方构建说明](https://github.com/ZJU-FAST-Lab/ego-planner-swarm#readme)

## 四条可行路线

| 路线 | 原生能力保真度 | 访客计算量和代价 | 对本站的用途 |
|---|---|---|---|
| 原生结果回放 | 回放的轨迹确实来自 EGO；访客改目标后不会在线重规划 | 很低；只按时间求位置和姿态 | 最适合先做的研究作品：障碍地图、轨迹、最近距离、规划耗时均可追溯到真实实验 |
| 独立 JS 近似规划 | 可以有避障、局部规划和样条，但除非完整实现并交叉验证，否则属于 EGO-inspired | 中；仍需 Worker 防止卡 UI | 适合教学交互，要明确标签，不能把演示计数当论文指标 |
| C++ 核心 → WASM → Worker | 可以保留优化成本、约束和算法流程；传感器及 ROS 外壳被适配 | 移植工作较大；有 CPU、地图缓存、启动成本 | 最接近无后端的原生体验，建议作为独立实验页面按需加载 |
| 独立 ROS 服务 + 浏览器轨迹客户端 | 可复用已有完整规划系统与研究环境 | 浏览器较轻，服务器承担计算；有网络延迟、部署和并发成本 | 适合预约演示或实验控制台；GitHub Pages 本身不运行 ROS 服务 |

GitHub Pages 是静态托管，支持浏览器下载 JS/WASM，不提供常驻 ROS 计算进程。[GitHub Pages 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

## RAM 与渲染资源要分开看

EGO 的地图和优化器主要消耗 CPU 时间及普通内存；Three.js 的贴图、网格、阴影和帧缓冲主要消耗图形资源。在统一内存设备上它们最终共享物理容量，但瓶颈仍应分开测。官方的 CUDA 选项服务于模拟深度传感器，并不是规划器必须依赖 CUDA；演示甚至默认使用简化运动模拟避免完整动力学的额外负担。[官方 GPU 与仿真说明](https://github.com/ZJU-FAST-Lab/ego-planner-swarm#4-use-gpu-or-not)

### 5 机、有限地图的计算预算示例（估算，非 benchmark）

假设局部地图 `40 m × 40 m × 10 m`，体素 `0.25 m`：共 `160×160×40 = 1,024,000` 个体素。

- 本地 `grid_map.cpp` 的六组主要缓存每体素至少 `8+1+2+2+1+1 = 15` 字节，单机约 **14.65 MiB**；5 份独立地图约 **73.24 MiB**。未含深度图、点云、容器、优化器、节点池和分配器开销。
- 如果演示共享一个已知静态地图，并只存一份 `Uint8Array` 膨胀占据信息，则该字段约 **0.98 MiB**。这是一项简化，不等价于每机独立感知、建图的原生系统。
- 默认 A*百万节点池按每节点约 **40–64 字节的结构大小假设**，仅节点内容约 **38–61 MiB/机**；5 机约 **191–305 MiB**，另有指针表和百万次分配开销。真实大小随 native/WASM ABI 和分配器变化，必须用目标构建测量。应改成有上限的紧凑池/按需分配，不照搬默认池。
- 将体素从 0.25 m 改成 0.125 m，在覆盖体积不变时占据缓存变成 **8 倍**。因此视觉地图可以很大，但规划局部窗口不宜跟着无限扩张。
- 5 机各保留 40 个三维 Float64 控制点，位置控制点总量只有 `5×40×3×8 = 4,800` 字节；knots、时间戳和姿态另计。轨迹回放本身远小于纹理或体素地图。

### 图形资源预算示例（估算）

未压缩 RGBA8 贴图含完整 mipmaps 时，约为 `宽×高×4×4/3` 字节。2K 约 **21.33 MiB/张**，4K 约 **85.33 MiB/张**；JPEG 文件只有几 MB 不代表显存只占几 MB。正常/粗糙度纹理的实际 GPU 格式由上传实现决定，这里用 RGBA8 作保守示例。两套环境各有一张 2K 色图和两张 1K 图，共约 **64 MiB**；若同时全部升级成六张 4K，则约 **512 MiB**，还没算几何、阴影和屏幕缓冲。

这不是当前整页实测值：主题资源加载策略与尺寸仍在迭代。应记录最终资源尺寸、唯一纹理/几何数量、缓冲字节和帧时间；不能把 `performance.memory` 的 JS heap 数值当作 GPU 显存。

提升写实感优先考虑真实扫描素材、合适的尺度、细节法线、光照和相机；不要用所有贴图一律 8K 或五架分别复制整套贴图来解决。材质/几何共享、只保留必要主题资源、压缩纹理和限制 DPR 更有助于控制预算。

## 如何避免交互卡顿

浏览器主线程只处理输入、相机和轨迹求值；Worker 负责规划。Worker 通过消息传递输出带 `requestId / mapVersion / startTime / trajectory` 的结果；过期目标结果必须丢弃，不能让旧规划覆盖新航点。大数组可用 transferable buffer 避免无谓复制。[Web Workers 官方用法](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)

初版建议一个普通 Worker 内的单线程 WASM，轮询调度 5 机，限制每次搜索节点数和优化迭代，测量后再考虑更多 Worker。Worker 不会使计算免费，手机仍会受 CPU 争用和发热影响。Pthreads 还需要 COOP/COEP 隔离响应头；不能假设静态托管当前已具备。单线程 WASM 放在普通 Worker 中不需要为 pthreads 配共享内存。[Emscripten 官方线程要求](https://emscripten.org/docs/porting/pthreads.html)

建议验收目标而非性能承诺：桌面交互帧间隔 P95 ≤ 33 ms；记录规划耗时 P50/P95/最大值、超时率与连续 60 秒内存峰值。规划任务初始设 100 ms 软预算并测真实完成率；超过预算应保留经过有效性检查的旧轨迹，旧轨迹失效或耗尽则进入停悬/停止演示，而非沿未经检查的直线前进。优化器需要支持中止或分段返回；仅在 Worker 外设一个计时器不能抢占长时间同步 C++ 调用。

碰撞验收应覆盖：航点位于障碍内、狭窄通道、两机对向、目标频繁重设、旧轨迹消息延迟、规划失败、暂停恢复。独立验证器检查速度/加速度与最小机间距离；渲染好看或平均 FPS 高都不能替代这些检查。

## 推荐下一步

1. 先从现有 ROS 实验导出一组真实 `Bspline`、障碍占据地图和时间戳；在独立研究页面提供回放、轨迹叠加和原始实验说明。主页仍使用现在的轻量巡航。
2. 用同一数据集验证浏览器 B-spline 求值：位置、速度、加速度在固定时间点与 C++ 输出逐项比较，明确世界坐标、单位和时钟转换。
3. 再提取无 ROS 的规划核心，先单机 Worker/WASM，通过障碍和失败场景，再扩大到 5 机。先缩减默认 A*节点池，后谈更多线程。
4. 只有达到资源和规划验收目标，才把“实时规划实验”作为探索模式的可选入口；加载失败保留主页和回放能力。
